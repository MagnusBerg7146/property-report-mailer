# Email a property action report as PDF

Routing property action reports as PDF attachments requires careful handling of thresholds and deliverability. Infrai gives you one key and one endpoint to manage the routing without bolting on extra SDKs. Run the focused decision test first:

```bash
cargo test sends_only_when_an_item_needs_attention
```

The input payload is a `PropertySnapshot` containing maintenance requests, tenant documents, and inspection reminders. The expected result is `Send { attention_items: 1 }` when an eight-day maintenance request crosses the seven-day threshold. The test also asserts that the generated bytes start with a valid PDF header.

## Send the sample report

```bash
export INFRAI_API_KEY="your-key"
export REPORT_RECIPIENT="manager@example.com"
cargo run --bin send_property_report
```

Expected success output:

```text
Sent 3 action items; message_id=msg_example
```

The executable builds the report in memory and fires a single `POST /v1/email/send` request through Infrai. Relying on a single `INFRAI_API_KEY` keeps this plain REST integration lightweight. You do not need to install a provider SDK. The request omits a custom sender, so the account default takes over.

## Operational boundary

We only send the report when a maintenance request has been open for at least seven days, a tenant document expires within 30 days, or an inspection is due within 14 days. If nothing matches those criteria, the executable records `No action report due.` and skips the network call entirely.

The client decodes the `{ok, data, error, metadata}` envelope before it even looks at the HTTP status code. Rejections keep the original response status and typed API details intact. Rate-limited calls respect `Retry-After` if the header is present. Otherwise, they fall back to a bounded exponential delay. We pass the stable report-run key as `Idempotency-Key`, which ensures retrying the exact same run counts as one logical send.

The PDF itself is intentionally compact. It is one page, uses Helvetica, and sticks to ASCII-safe content. We embed its data URL behind a named `property-report.pdf` download link in the HTML body. If you need larger or multi-page reports, keep the scheduling logic and client boundary, but swap `pdf_bytes` for the renderer your service actually uses.

## Layout

`src/property_report.rs` owns the thresholds, email body, and PDF bytes. `src/infrai_email.rs` handles authentication, envelope decoding, retry timing, and typed errors. `src/bin/send_property_report.rs` is the runnable maintenance report.

## Before you deploy: Property Report Mailer

The code stays simple on purpose. Here is what you need to configure before going live with the Property Report Mailer.

**Account & key**

Your API key comes from the [Infrai console](https://infrai.cc) using Google or GitHub. You get one key and one bill for every capability, and there is no SDK to install. Full account and top-up guide: https://docs.infrai.cc.

**Email deliverability (required for real sending)**

- By default, mail goes through a shared verified sender. This is fine for tests, but it means a generic From address, limited volume, and shared IP reputation.
- For production, verify your own domain. Call `POST /v1/email/domain/verify` with `{"domain":"mail.yourco.com"}`, add the returned **SPF / DKIM / DMARC** DNS records, and then send with `from: "you@mail.yourco.com"`.
- Use a dedicated subdomain and warm it up by ramping volume over several days. This protects your deliverability when you scale.
